## Architecture summary

GitPulse is a React 19 / TypeScript / Vite single-page application configured for the `/GitPulse/` deployment base. `AppShell` composes account input, connection controls, moods, a contribution grid and media bar, the visual field, and insights. Tailwind and reusable UI primitives provide styling; Zustand holds identities, normalized datasets, authentication state, mixer settings, and playback position.

Data flows through `src/github`: public REST profile/repository/language fetching and optional authenticated GraphQL contribution calendars feed normalizers and merge helpers. The domain dataset preserves source attribution, deduplicates repositories, and distinguishes actual contribution calendars from approximate repo-push activity. Demo data is available without authentication.

Pure audio mapping and contribution sequencing derive deterministic patterns from the dataset. `ContributionMediaBar` is the active transport UI. The singleton Tone.js engine lazily loads audio, starts from explicit interaction, schedules contribution days, and routes instruments through a shared master and limiter. The analyser taps the limiter output and supplies waveform, frequency, RMS, and band-energy snapshots.

`useAudioAnalyser` polls through animation frames and updates React state at a target 30 Hz, or 18 Hz with reduced motion. React Three Fiber renders layered heartbeat lines using the sampled signal. WebGL fallback UI is present. Visuals currently respond to audio; repository orbit/data-driven visual mapping remains future scope.

The separate Cloudflare Worker brokers OAuth code exchange; browser code manages OAuth state and session storage. No general backend or database is present. Root CI runs lint, formatting checks, typechecking, tests, and build for pushes/PRs targeting `main`; the Worker has its own package and TypeScript configuration.

## Findings, ordered by priority

### 1. P2 — New debug storage access can stop visual updates

Evidence: [audioAnalyser.ts:122](../src/audio/audioAnalyser.ts#L122), [audioAnalyser.ts:243](../src/audio/audioAnalyser.ts#L243), [useAudioAnalyser.ts:26](../src/audio/useAudioAnalyser.ts#L26), and [HeartbeatTrace.tsx:73](../src/visuals/HeartbeatTrace.tsx#L73).

Every snapshot checks `window.localStorage.getItem(...)` without exception handling, including silent/unattached snapshots. When storage access throws, `getSnapshot()` throws before returning. The polling callback schedules its next frame after that call, so the exception can stop polling. The trace effect also invokes this helper. This makes an optional debugging feature a dependency of normal rendering even when the flag is not enabled.

An isolated execution with a synthetic throwing storage getter reproduced `getSnapshot threw storage access denied`. No real browser storage was accessed. Follow-up: treat unavailable storage as debugging disabled and cover this condition in a regression test.

### 2. P2 — Frame smoothing overshoots and uses inconsistent amplitude limits

Evidence: [heartbeatSignal.ts:57](../src/visuals/heartbeatSignal.ts#L57), [heartbeatSignal.ts:193](../src/visuals/heartbeatSignal.ts#L193), [heartbeatSignal.ts:219](../src/visuals/heartbeatSignal.ts#L219), and [HeartbeatTrace.tsx:53](../src/visuals/HeartbeatTrace.tsx#L53).

The normal smoothing factor is `1.46`. Applying `previous + (target - previous) * factor` extrapolates beyond the target. An isolated check with previous value `0.2` and silent target `0` produced `-0.092`: a sign reversal instead of monotonic decay. For a fixed target, this factor yields decaying oscillation, not unbounded divergence, but it can amplify changes between sampled frames.

The first frame uses the configured cap (`1.28`, or `0.6656` with reduced motion). Later frames call `clampVisualSample` without specifying a cap and therefore clamp to `0.32` in both modes. A synthetic strong constant waveform reproduced first/second peaks of `1.28/0.32` normally and `0.6656/0.32` with reduced motion. In ordinary playback, previous history already exists, so the persistent lower cap can flatten stronger signals and defeat the intended amplitude tuning.

None of the current heartbeat tests supplies `previousSignal`. The reduced-motion amplitude test only exercises the first-frame path. Follow-up: define a consistent amplitude policy and a frame response that matches the intended damping; test transitions over multiple frames before further visual tuning.

### 3. P2 — Existing contribution refresh can apply stale authenticated results

Evidence: [useGitPulseStore.ts:381](../src/store/useGitPulseStore.ts#L381), [useGitPulseStore.ts:423](../src/store/useGitPulseStore.ts#L423), and [useGitPulseStore.ts:432](../src/store/useGitPulseStore.ts#L432).

A refresh captures the token, awaits requests, and then applies results to current identities without checking whether the token or request generation changed. Disconnecting during a pending refresh can clear calendars and then have the old response restore them. Overlapping refreshes can also finish out of order. This predates the five-file diff and is a source-level finding, not an exercised network scenario. Follow-up: invalidate outstanding refreshes on disconnect/token changes and add deferred-promise tests with mocked requests.

### 4. P2 — Worker validation is outside the root CI checks

Evidence: [.github/workflows/ci.yml](../.github/workflows/ci.yml), [tsconfig.json](../tsconfig.json), and [worker/package.json](../worker/package.json).

Root TypeScript references cover the frontend and Vite config, not `worker/tsconfig.json`. CI does not invoke the Worker's typecheck, and no Worker test files were found. Root ESLint may inspect Worker TypeScript syntax, but that does not replace its typecheck or broker behavior tests. This is an existing coverage gap. Follow-up: validate the Worker separately and test method/origin/redirect restrictions plus failed upstream exchanges using mocks.

### 5. P3 — Repository summaries cover a limited fetched sample

Evidence: [githubClient.ts:37](../src/github/githubClient.ts#L37) and [githubClient.ts:93](../src/github/githubClient.ts#L93).

Repository fetching requests one page of up to 100 repositories without pagination. Detailed language requests cover only the first 24. Large accounts can therefore have incomplete repository/star/fork summaries and sampled language statistics. This is existing behavior, separate from the documented approximate contribution timeline. Follow-up: explicitly label the sampling limits or implement pagination with an appropriate request budget.
